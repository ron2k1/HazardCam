Each `data/prepared/<id>/expected.json` is judge-only and contains:

- `category`, `event_type` and `accepted_event_types`;
- `abstention_acceptable`, false only for positives;
- `time_window` (seconds in the clip, clamped to it, with a flag);
- `region`: `zone_id`, `accepted_zone_ids`, `event_point_local_m` and an uncertainty of 5 m;
- `direct_visibility` per visible camera;
- `indirect_cues`: concurrent visible-camera annotations within 30 m;
- `derivation`: MEVA activity ids, frames and clip names;
- `evidence_frames`, pointing at `evidence/contact_sheet.jpg`.

Each manifest carries provenance with:

- the MEVA license and attribution;
- the per-file source clip and URL, trim offset, sync method and uncertainty;
- camera height, pitch and ENU position;
- ffprobe media info.

## Assumptions and caveats for the integrator

1. **Eval manifests are listed as scenarios.** `data/manifests/` holds all 22, so the API lists `eval_*` next to
   `scenario_001`. If the dashboard should show only the flagship, filter by id prefix or move the evals to another
   directory in the integration step. They have to stay out of `data/manifests` only if the UI must not list them;
   the format is identical.
2. **The mp4 files are gitignored** (`data/prepared/**/*.mp4`). Ship them in the offline bundle, or regenerate them on
   the event machine (about 10.5 GB raw download plus about 5 minutes of CPU). The `expected.json` and contact-sheet
   files are small and committable.
3. **Sync is ±1 s across cameras**, from the MEVA wall-clock filenames. The clip-table README states the offset sign
   backwards; the code follows the data, with evidence in `research.md`. Cross-camera motion correlation is weak
   (ncc 0.2–0.45 for non-overlapping views), so it is not an independent sync check.
4. **Geometry error.** KRTD positions are good to about 1–3 m and 1–2 deg; mapped event points to about 2–5 m.
   G436's calibration differs by date (heading 350 deg on 03-07, 358.5 deg on 03-15), so `cam_b`'s pose differs
   slightly between scenarios. That is real, not a bug.
5. **Visibility test resolution.** The direct-visibility test assumes a 1080 px image height. G506/G505 are actually
   1072 px, an 8 px edge difference. Several ambiguous cases sit within a few metres of a footprint edge, and their
   notes say so.
6. **What the cues are.** `indirect_cues` lists concurrent annotated activity near the event, not proven reactions.
   Cars seen entering or leaving and pedestrians walking toward the pocket are the real cues, and they are described
   by inspection only in the notes.
7. **Labels the models can see.** Titles, zone labels and camera labels are neutral (wall-clock time, place names).
   The MEVA camera ids appear in visible-camera labels and the GT label, and the GT label is redacted by the existing
   guard. Dataset activity names appear only in `expected.json`.
8. **Motion z-scores.** G340's motion z-scores are very large because the static lot plus near-field pedestrians give
   a tiny MAD. Rank motion within each camera, not across cameras.
9. **XML parsing.** `fetch_meva.py` parses the public S3 XML listing with stdlib ElementTree. defusedxml is not a
   dependency and none could be added. The input is AWS's own listing response, used only at acquisition time.
10. **Event taxonomy.** The `event_type` vocabulary is
    `passenger_dropoff_pickup | vehicle_turnaround | vehicle_loading_unloading | vehicle_departure | none`, with
    `accepted_event_types` synonyms. The eval harness should map hypotheses onto these, and treat `unknown` or
    abstention as correct wherever `abstention_acceptable` is true.
