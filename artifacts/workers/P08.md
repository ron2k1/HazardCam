## Bundle assembly (integrator addendum)

`assemble_evidence_bundle(view, evidence, clusters, candidates, *, min_cameras=2, notes=None)` is the only place the ok/insufficient rule lives. It builds the `BundleCamera` list from the view and derives the output-side notes, without re-correlating or re-triangulating. `build_evidence_bundle` is now correlate, then `triangulate_region`, then `assemble_evidence_bundle(notes=correlation.notes())`.

- **Status rule**: `ok` iff some cluster's *evidence items* span `>= min_cameras` distinct cameras. Cameras are counted from the cited evidence, so a cluster cannot inflate its own `camera_ids`. The two counts are identical for correlator-produced clusters.
- **Guard**: every camera id cited by evidence, clusters or candidates must be in the view, or `GroundTruthAccessError` is raised. A raw `Scenario` is refused. A cluster citing unknown evidence raises `ValueError`. The output is schema-validated before return.
- **Inputs**: models or their JSON dicts (the event-day agent passes tool results as JSON).

Notes come in two kinds:

- **Input-side** (no batches supplied, observations dropped below `min_confidence`, id renames): only the batches know these, and the binding `correlate_observations` tuple cannot carry them. Two paths record them:
  - `build_evidence_bundle`
  - the split path: `fusion_notes(batches, view, *, min_confidence)`, passed as `assemble_evidence_bundle(..., notes=...)`. It reruns the cheap correlation and returns `Correlation.notes()`, so the wording is identical. Drops and renames do not depend on `tolerance_s`.
- **Output-side** (silent cameras, missing bearings, insufficient, no or single-ray region): derived inside `assemble`. Caller notes come first.

Equivalence is tested by checking that the split path gives byte-identical bundle JSON to `build_evidence_bundle` in three cases: the fixture data; fixture plus a dropped observation and an id collision, under default and custom kwargs; and empty batches. The insufficient note no longer quotes `tolerance_s`, because `assemble` does not receive it.

## Bearing table (compass deg, h = heading, f = fov)

| direction | bearing | needs |
|---|---|---|
| left / center_left / center / center_right / right | h - 0.4f / h - 0.2f / h / h + 0.2f / h + 0.4f | heading + fov |
| toward_camera, away_from_camera | h (optical axis; ray weight x0.5) | heading + fov |
| north, northeast, ..., northwest | 0, 45, ..., 315 | nothing |
| null / unknown word / missing geometry | None | - |

The five image-relative values are the centers of five equal 0.2f bands (linear-in-angle approximation). Matching ignores case and maps `-`/space to `_` (`"Center-Left"`, `"North East"`). Results are wrapped to [0, 360).

## Formulas

- **Scenario time**: `t + camera.time_offset_s`, rounded to 1 us.
- **Confidence filter**: an observation is dropped iff `confidence < min_confidence` (the threshold itself is kept).
- **Linking**: single-linkage, where two items link iff the gap between their intervals is `<= tolerance_s` (inclusive, 1e-9 epsilon). This is computed by a sorted sweep with a running max end, which gives exactly the connected components. Cluster ids `clu_01..` follow `t_start`, and every evidence item is in exactly one cluster.
- **Cluster score**: `0.5 * cams/visible_cams + 0.3 * mean_conf + 0.2 * tightness`, with `tightness = 1 / (1 + onset_spread / max(tolerance_s, 0.1))`. Rounded to 4 dp.
- **Rays**: origin = camera position. Weight = confidence (x0.5 axial). Angular half-uncertainty sigma = 0.1f lateral, 0.5f axial, 22.5 deg compass or unknown, capped at 45 deg.
- **Crossings**: taken pairwise between different cameras. A pair is skipped when it crosses at < 5 deg (near-parallel or anti-parallel) or lies behind either camera.
- **ray_intersection**:
  - center = mean of the crossings, weighted by `w_a * w_b`
  - `radius = max(3 m, hypot(spread_rms, angular))`, with `angular` = weighted mean of `hypot(r_a tan sa, r_b tan sb) / sin(angle)`
  - `score = cluster.score * (0.5 * agreement + 0.5 * 3 / radius)`, with agreement = cameras in a valid crossing / cameras with rays
- **No valid crossing**: use the strongest ray (weight, then evidence id).
  - If the ray passes within the radius of a zone whose center lies ahead of the camera, the result is `zone_prior` (zone center/radius/id/label, `score = cluster.score * 0.5`).
  - Otherwise it is `single_ray`: a point 15 m along the ray, radius 15 m, `score = cluster.score * 0.25`.
- **Which clusters**: the top 3 clusters by score that have at least 1 ray.
- **Zone snap** (ray_intersection): the center inside a zone takes that zone's id and label, and keeps the computed center and radius. With overlapping zones, the smallest dist/radius wins.
- **Candidate order**: sorted by score desc, then cluster id. Only the best candidate per zone id is kept. Other candidates get `region_NN`, skipping view zone ids.
- **Bundle status**: `ok` iff some cluster's evidence spans `>= min_cameras` (default 2) distinct cameras. This is applied only in `assemble_evidence_bundle`.

## Evidence id rule

- Ids are kept verbatim.
- An id emitted by 2+ cameras becomes `<camera_id>:<id>` on every copy.
- A repeat within one camera becomes `<id>#2`, `#3`... in canonical content order.
- Every rename is listed in `Correlation.renamed` and in a bundle note.

## Assumptions

- A ray starts at the camera position, not at the cue's image location. That is coarse by design.
- `toward_camera`/`away_from_camera` are treated as cues on the optical axis rather than as None.
- Input-order invariance is tested for both evidence/clusters and the full bundle JSON (20 shuffles each).
- Fusion tools accept only `ModelScenarioView`. A raw `Scenario` raises `GroundTruthAccessError`, and so does any batch or evidence whose camera is not in the view (checked even for empty batches).
- `build_evidence_bundle` validates its own output against `contracts/evidence.schema.json` before returning, so it fails closed.

## Blocker / proposal for the integrator (files outside my paths)

The fixture has a mismatch. In `data/fixtures/qwen_observations.json`, cam_01 (heading 95) says `"west"` and cam_02 says `"northwest"`. Those rays only meet behind cam_01, so fusion correctly yields a `single_ray` `region_01` at (-15, 4). `data/fixtures/final_hypothesis.json` cites `"region": "blind_zone_02"`, and `tools/submit.py` demotes any non-candidate region to `"unknown"`. As a result, fixture-mode E2E will show region `unknown`.

Proposed fix, verified by `test_geometrically_consistent_fixture_directions_snap_to_blind_zone_02`: set the fixture directions to cam_01 `"right"`, cam_02 `"west"` and cam_03 `"center_left"`. That yields `blind_zone_02` via `ray_intersection` from all 3 cameras, with center (4.335, 0.609). If the fixture changes, `test_fixture_observations_give_schema_valid_ok_bundle` needs its region/bearing assertions updated to match.
