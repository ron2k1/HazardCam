## Assumptions and limitations

- The offline check proves the fixture path needs no network. It patches Python
  sockets in-process, so it does not cover subprocesses or the Windows Proactor
  `ConnectEx` path; the web build is checked statically for remote font and CDN hosts.
- No aarch64 bundle for the GB10 was built. The Python wheels, `node_modules` and the
  Ollama binary here are x86-64 Windows builds (the GGUF model files themselves are
  portable); the GB10 needs its own `uv sync --frozen`, `pnpm install` and model pulls,
  listed in `QUICK_COMMANDS.md`. `uv sync --frozen --dry-run` reports no
  changes against this laptop's `.venv`, so the lockfile reproduces the tested set.
- `start_app.sh` is a Git Bash / Linux script. On Windows it stops the server trees with
  `taskkill -F -T` on the Windows PID; elsewhere, or when `taskkill` fails, it TERMs each
  server's process group, waits up to `STOP_GRACE_S` (10 s), then KILLs.
- A SIGTERM sent to the script while `next build` runs takes effect when the build ends
  (bash runs a trap only between foreground commands). Ctrl+C in the terminal reaches the
  build directly, and the script then stops the API.
- In a container whose PID 1 does not reap children, a stopped server stays a zombie, and
  the stop reports it still running after the KILL grace. Run the container with an init.
- The port check before start and the servers' bind are not atomic: another process can
  take a port in between, and the server then fails to bind.
